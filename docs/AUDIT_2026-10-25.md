# Deep-dive audit — 2026-10-25

*Scope: every part of the pipeline between "user drags a finger on the phone" and "pixels",
plus the input/generation side. Triggered by: avatar still corrupt on Samsung SM-S921B, new
screen flicker, missing diagnostics menu, and a device screenshot showing corruption on the
**Vulkan** backend (`artifacts/device-vulkan-corruption-2026-10-25.jpg`).*

## Findings

### F1 (root cause of "avatar is still corrupt") — CI shipped a stale prebuilt renderer

The APK the device ran was built with `-Paf.prebuiltJni=prebuilt/`, which **skips the CMake
native build and packages the committed `prebuilt/arm64-v8a/*.so`**. Those binaries were
committed in the base commit (2026-10-22) — **before every renderer fix** (camera UBO stride,
VAO binding, hardening). The device therefore never ran fixed code, and no CI run had ever
compiled `native/src/render/` at all.

*Fix:* `.github/workflows/android-apk.yml` now drops `-Paf.prebuiltJni` and builds the three
libraries from source (Gradle→CMake, `-Paf.parallel=4`, 45 min timeout). The `prebuilt/`
directory remains a documented low-RAM local convenience only. **The next CI APK is the first
build that can actually contain the fixes.**

### F2 — device screenshot analysis (Vulkan path)

`artifacts/device-vulkan-corruption-2026-10-25.jpg` (from the 0.10.1 app, header reads
"vulkan · Samsung Xclipse 940 · 58 FPS"):

- Silhouette is roughly humanoid ⇒ `viewProj` (bytes 0–63 of the camera UBO) was intact.
- Chrome-white head, moiré/wavy cloth shading, patchy skin-through-pants ⇒ everything *after*
  byte 256 of the camera UBO was garbage: `lightViewProj` (tail), `cameraPos`, `sunDir`,
  `envFlags`, `uiParams`. Exactly the torn region of the pre-fix UBO layout
  (`CameraUbo` = 448 B, slice stride 256 ⇒ frame N+1's write at 256 clobbers frame N's
  256–448 and runs to 704 on a 512-byte buffer).
- The alternating per-frame garbage also explains the **flicker**: lighting/environment data
  flips between frames.
- Blocky gauntlets are the generated "armor plate" geometry (kernel generation quality, see
  F9), not renderer corruption.

### F3 — flicker regression in the GLES hardening (fixed this round)

The earlier "hardening" treated **any** pending GL error as fatal context loss and rebuilt the
entire EGL context + programs + buffers + targets. On a driver with a persistent benign error
that loops every frame: error → teardown → same error → teardown ⇒ screen flicker. It also
single-polled `glGetError()` (leaving later errors queued) and forced a full 35 MB mesh +
atlas re-upload on every `resize()` (VBOs/atlas textures survive a resize — only render
targets are rebuilt).

*Fix (`af_gl.cpp`):*
- `drainGlErrors()` flushes the **whole** queue, counts into `stats_.glErrorsTotal` and records
  `stats_.lastGlError` (GLenum) for the diagnostics panel.
- A plain GL error **no longer tears anything down**; only EGL-layer signals
  (`EGL_CONTEXT_LOST` / `EGL_BAD_SURFACE` from `eglSwapBuffers`) set `contextLost_`.
- Recovery is bounded (`recoverAttempts_ < 5`) so a failing rebuild path stops instead of
  flickering half-rebuilt frames forever.
- `resize()` no longer re-uploads geometry/atlas.

### F4 — camera could not be moved (fixed `6659c8f`)

`pointerInput(Unit)` runs once and keeps first-composition captures, so the orbit gesture
computed every drag from the initial pose (180°/4°/3.0 m). Fixed by routing the gesture
through a `remember`-held `liveCamera` state synced from the host parameter.

### F5 — diagnostics menu restored

The 0.10.1 app had a "≡ MENU" (visible in the screenshot); this tree never had it. Restored:
- `≡ MENU` top-right in the viewer → **Diagnostics** / **Renderer settings** / **Copy device
  report**.
- New `DIAGNOSTICS` viewer panel: backend line, GPU features, **GL error count + last error
  code (newly plumbed: `RendererStats.glErrorsTotal/lastGlError` → JNI 9 ints → Kotlin)**,
  live frame stats, model counters, and the `AvatarForge.deviceReport()` paragraph with a
  copy-to-clipboard button.

### F6 — renderer code was never compiled anywhere (process hole, closed)

Because of F1, renderer commits reached the device unverified by any compiler. Added
`tools/syntax_check/run.sh`: `g++ -fsyntax-only` over all five renderer/JNI translation units
using stub EGL/GLES3/android headers + real Vulkan (Khronos) and JNI (OpenJDK) headers.
**All five TUs parse clean** (this round's changes included).

### F7 — backend default flipped to GLES 3.1 (per user instruction "don't use Vulkan")

`RendererOptions.preferVulkan` (C++), `RenderSettings.preferVulkan` (Kotlin) and
`AvatarForge.recommendedSettings()` now default to **false** ⇒ GLES 3.1 primary. Vulkan stays
available as an opt-in toggle in the RENDER panel (takes effect on viewer restart). Rationale
recorded in the code: the Xclipse 940 Vulkan driver corrupts the forward pass on this device.

### F8 — Vulkan device-loss is not recoverable (known limitation, documented)

`af_vk.cpp` returns early on `VK_ERROR_DEVICE_LOST` (acquire/submit/present) but does not
re-initialise the device; the renderer stays dark until the host recreates it. Acceptable while
Vulkan is off by default; a full device-rebuild path remains future work.

### F9 — generation quality (kernel side, separate track)

The screenshot's blocky "hands" are the armor-gauntlet SDF output for the "armor plate sabaton"
spec; the head proportions for that spec are also weak. This is kernel generation quality, not a
renderer bug — the renderer draws exactly what the kernel exports (world-space vertices, CPU
skinning). Tracked separately; not addressed in this round.

### F10 — model import pipeline (verified, no bug)

`importIntoEngine()` sets `vertsRest` then clears `restMesh`/`rig`: imported GLBs expose
bind-pose via `vertices_rest()` but have an empty rig, and `applyCurrentPose` returns
`AF_ERR_NOT_READY` for static imports — expected behaviour. The Rust end-to-end test now
compares against `vertices_rest()` (`928491f`).

## Device retest checklist (needs the SM-S921B)

1. Install the **next** CI APK (the first one containing compiled fixes) — verify the header
   reads `gles31`.
2. Avatar should render with stable lighting; the white head / moiré cloth should be gone
   (the blocky gauntlets may remain — that's F9, generation quality).
3. Drag orbits and holds; pinch zooms; taps pick.
4. Diagnostics → GL errors line: expect `0 total · none` while idle and while dragging.
5. If anything still corrupts: Diagnostics → *Copy device report*, plus the GL error count/code
   from the panel — that identifies the rejected call without needing the device again.
