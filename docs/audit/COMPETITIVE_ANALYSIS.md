# AvatarForge competitive technology analysis

**As of:** 2026-10-30
**Scope:** engineering comparison for maintainers; no technology below is claimed to be integrated into AvatarForge or superior to its current design.

## Methodology and verification boundary

This report synthesizes the supplied successful research results. The cited authoritative project pages, specifications, manuals, release pages, licenses, Android documentation, and AvatarForge repository pages were opened/fetched and used for the claims immediately adjacent to their links. The comparison keeps AvatarForge’s stated architecture in view: a custom C++17/native and JNI pipeline, offline/no-network operation, custom Vulkan-primary plus OpenGL ES 3.1 fallback rendering, and GLB/glTF import/export ([AvatarForge README](https://github.com/davealone69-gif/AvatarForge), [BUILD.md](https://raw.githubusercontent.com/davealone69-gif/AvatarForge/main/BUILD.md)). AvatarForge’s own status says the renderer has not executed on a physical Android GPU and that device rendering, GPU timing, pixels, memory, and thermal results remain unverified ([STATUS.md](https://raw.githubusercontent.com/davealone69-gif/AvatarForge/main/STATUS.md), [DEVICE.md](https://raw.githubusercontent.com/davealone69-gif/AvatarForge/main/DEVICE.md)).

No head-to-head benchmark, physical-device run, APK comparison, thermal soak, pixel comparison, or AvatarForge integration was performed for this report. Consequently, “UNVERIFIED” means the supplied sources do not establish the field; it is not a negative test result. No external project was tested in AvatarForge, and no superiority claim is inferred from feature lists, repository activity, or documentation. The supplied research reported **no failed research items**; “not researched” or “UNVERIFIED” fields below remain explicit where evidence was absent.

## Baseline: what a candidate must improve or preserve

AvatarForge’s target is not an interchangeable game-engine demo. Any proposal must preserve, or deliberately justify changing, the custom native/JNI boundary, offline build and runtime rule, GLB pipeline, generated avatar skeleton/morph/clip semantics, Vulkan/GLES fallback policy, deterministic diagnostics, and eventual API-26+ packaging. AvatarForge’s repository reports a custom Vulkan-primary/GLES-3.1-fallback renderer and host/static verification, but no physical-device proof ([README](https://github.com/davealone69-gif/AvatarForge), [STATUS.md](https://raw.githubusercontent.com/davealone69-gif/AvatarForge/main/STATUS.md)). Existing device gates proposed by the project are useful validation inputs rather than achieved results: renderer identity, Vulkan or GLES 3.1, jank under 5%, p95 frame time under 33.3 ms, process memory under 1.5 GB, zero crashes, and no SEVERE/CRITICAL thermal state during the defined soak ([DEVICE.md](https://raw.githubusercontent.com/davealone69-gif/AvatarForge/main/DEVICE.md)).

## Detailed adoption / avoid / benchmark guidance

### Adopt or adapt now: contracts and measurement infrastructure

1. **Keep the custom architecture as the control.** glTF 2.0 is the strongest common contract for AvatarForge’s generated meshes, PBR materials, skins, morph targets, animations and GLB packaging, but it does not supply a renderer or runtime policy. Define an explicit supported subset and validate hostile/malformed files before expanding extensions ([glTF specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html)).
2. **Treat Android Vulkan guidance and ADPF as validation/instrumentation inputs, not replacement technologies.** Add capability/version guards, validation layers, frame-pacing evidence and thermal/quality policy only through isolated changes. API 26 fallback behavior is mandatory because the useful thermal/performance APIs arrive later ([Vulkan native guidance](https://developer.android.com/games/develop/vulkan/native-engine-support), [ADPF](https://developer.android.com/games/optimize/adpf)).
3. **Prioritize measurable truth over feature-count comparisons.** Before adopting any renderer or optimization, make the device report capture backend identity, successful first paint, CPU and GPU timing when genuinely available, p50/p95/p99 frame time, jank, PSS/native memory, startup/first-frame time, crashes, asset correctness, and thermal status. Unsupported fields must stay UNVERIFIED/UNAVAILABLE rather than zero ([AvatarForge DEVICE.md](https://raw.githubusercontent.com/davealone69-gif/AvatarForge/main/DEVICE.md)).

### Benchmark before adoption

- **Filament, bgfx, Godot:** use only disposable adapters/harnesses initially. Their documented Android/backend/asset capability does not establish compatibility with AvatarForge’s custom lifecycle, generated avatars, materials, or no-network build. Compare against the current renderer on identical scenes and devices.
- **meshoptimizer, KTX-Software, ozz-animation:** isolate each at its natural boundary—geometry/GLB optimization, texture distribution, or animation sampling. Do not combine changes in the first experiment; otherwise memory, CPU, GPU and visual effects cannot be attributed.
- **Blender:** benchmark the exported asset contract, not Blender runtime. A minimal fixture should include known rest pose, one action, representative skin weights, shape keys, PBR textures and GLB validation.
- **ADPF:** benchmark paired policy runs, not API call overhead alone. Confirm that thermal response is caused by the policy and not by different workload duration or ambient conditions.
- **LiteRT:** benchmark only a frozen model at a documented tensor boundary. Include preprocessing, copies, inference, postprocessing and the existing renderer in the end-to-end trace.

### Avoid or defer

- **Avoid wholesale engine replacement** by Lugdunum, Godot, Filament or bgfx until a migration prototype proves asset/lifecycle correctness and a net device benefit. Lugdunum is explicitly unmaintained and has the highest maintenance concern among the renderer candidates ([Lugdunum README](https://github.com/Lugdunum3D/Lugdunum)).
- **Do not treat LiteRT as a 3D renderer**, KTX as an animation system, meshoptimizer as a renderer, Blender as an Android runtime, glTF as a Vulkan/GLES implementation, or ADPF as a performance guarantee.
- **Do not enable compressed/quantized/optimized asset paths unconditionally.** Preserve a lossless/reference path and use feature gates until target-device pixels, memory, decode time and thermal behavior are measured.
- **Do not claim offline reproducibility from upstream availability alone.** Maven/AAR, host tools, model artifacts, texture encoders and transitive notices must be pinned, cached and built in an offline clean-room test.

## Prioritized validation plan with measurable criteria

### P0 — establish a reproducible device baseline

1. Select named representative arm64 devices: at least one API-26–28 GLES/Vulkan-limited tier, one API-29+ Vulkan-capable tier, and one current higher-performance tier. Record OS build, GPU/driver, ABI, backend, display resolution and thermal starting state.
2. Run the unchanged AvatarForge build with a fixed representative GLB containing the production skeleton, morph targets, PBR textures and authored clips. Use fixed camera, lighting, resolution, animation/orbit trace and duration.
3. Capture: first-paint success and time; backend identity; CPU frame time; GPU frame time only from valid slices/counters/timestamps; p50/p95/p99 frame time; jank; draw/triangle counts; process PSS/native/graphics memory where available; APK/native/asset bytes; crashes; thermal status/headroom when supported; and deterministic screenshots.
4. Baseline acceptance is the project’s declared gate—p95 <33.3 ms, jank <5%, PSS <1.5 GB, zero crashes, no SEVERE/CRITICAL thermal status—while recording any unavailable field as UNVERIFIED ([DEVICE.md](https://raw.githubusercontent.com/davealone69-gif/AvatarForge/main/DEVICE.md)). If the baseline itself cannot run on hardware, no candidate can be declared superior.

### P1 — asset and animation correctness

For glTF/Blender/Filament/Godot/ozz/meshoptimizer candidates, create a golden corpus: AvatarForge-generated GLB, one Blender-authored GLB, one core skin+morph reference, malformed/hostile files, and representative textures. Verify GLB structure, joint count/order, inverse binds, rest-pose error, skin deformation, morph displacement and naming, clip duration/sampling/loop continuity, material/texture color and alpha, and round-trip output. Require zero missing required joints/clips, zero importer crashes, and pose/image differences within a predeclared tolerance. A valid file parse alone is not sufficient evidence of render compatibility.

### P2 — renderer/backend A/B

For Filament, bgfx, Godot, and Vulkan-path experiments, hold device, GLB, camera, lights, resolution, animation, quality settings and interaction trace constant. Run repeated warm and cold trials. Report per-device p50/p95/p99 CPU/GPU frame time, jank, first frame, crashes, PSS, package size, and screenshots. A candidate may proceed only with zero correctness/lifecycle failures and a repeatable pre-registered improvement—default proposal: at least 10% lower p95 GPU frame time, or an explicitly approved equivalent quality/feature gain—with no project-defined memory or thermal regression. This is a proposed gate, not an achieved result.

### P3 — memory and texture experiments

For KTX2/Basis and meshoptimizer, compare baseline PNG/unoptimized GLB against one change at a time. Measure packaged and decoded bytes, peak PSS/native/graphics memory, parse/decode/transcode/upload CPU time, valid GPU timing, draw/triangle counts, screenshots of base-color/normal/metallic-roughness/alpha regions, and fixed-duration thermal behavior. Require the intended byte or memory reduction on every selected tier, material-pixel parity within tolerance, no new unsupported-texture/asset path, and no p95/jank/thermal regression.

### P4 — animation runtime experiment

For ozz, compare the current animation kernel against an isolated adapter using identical skeleton, clips and joint count. Measure sampling/blending/local-to-model/skin preparation CPU time, animation bytes, load time, random-seek latency, PSS, pose/vertex error, and export preservation. Require equivalent pose/vertex output and no missing clips/joints, plus a repeatable improvement in the selected CPU or byte metric without worse PSS or thermal class.

### P5 — sustained thermal and adaptive-policy experiment

Run ADPF-off/on paired trials with the same backend, scene, animation and duration. Record target/actual work duration, frame distributions, jank, thermal transitions, headroom samples at a sensible cadence, quality/LOD changes, PSS, battery/temperature proxies and crashes. Accept only if the policy improves sustained pacing or avoids severe throttling without unacceptable visual or correctness regression. On API 26–28, verify the no-op/fallback path; on API 29–35, verify each API-gated feature independently.

### P6 — optional ML boundary experiment

Only if product requirements identify a tensor model, compare current processing against LiteRT Interpreter/CompiledModel and available delegates using a frozen corpus. Measure initialization, warmup, steady-state and end-to-end p50/p95 latency, tensor-copy cost, output parity, model/APK size, peak PSS, accelerator actually selected, concurrent renderer frame time, crashes and thermal soak. Adopt only if the selected stage improves at p95 with output parity and no unacceptable memory/thermal regression; otherwise keep the existing offline implementation.

## Source, licensing and maintenance caveats

Licenses are not interchangeable with integration permission. Filament is Apache-2.0; bgfx BSD-2-Clause; Lugdunum, meshoptimizer and ozz MIT; Godot MIT; LiteRT Apache-2.0; Blender software GPL with separate treatment for created artwork/data; glTF/KTX repositories contain mixed specification/tool/dependency licensing; KTX specifically includes a non-open-source Ericsson ETC decoder exception in its tree. Each candidate requires a release NOTICE/third-party audit before distribution. AvatarForge’s own repository says its license has not yet been chosen, which is an independent release blocker for publishing or redistributing AvatarForge code ([AvatarForge contents](https://api.github.com/repos/davealone69-gif/AvatarForge/contents)).

Repository activity is only a maintenance signal, not a compatibility or quality guarantee. Conversely, Lugdunum’s explicit unmaintained status is a material risk. Exact versions, ABI stability, transitive dependencies, offline caches, host tools, shaders, model/texture encoders and generated artifacts must be pinned before any adoption decision.

## Final maintainer decision

Retain AvatarForge’s custom C++17/JNI, offline, Vulkan-primary/GLES-3.1-fallback architecture as the control and near-term implementation. **Adapt glTF conformance and measurement discipline first.** Treat Filament, bgfx, Godot, meshoptimizer, KTX-Software, ozz-animation, Blender, ADPF and LiteRT as bounded benchmark or workflow candidates with clearly different scopes; treat Lugdunum as historical reference only. No candidate should be called an improvement until the P0–P6 evidence exists on physical devices, with unsupported measurements explicitly reported as UNVERIFIED and with no head-to-head or integration result inferred from this document.
